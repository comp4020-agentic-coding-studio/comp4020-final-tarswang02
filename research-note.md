I propose that multiple agents are most useful when they build and question check rules together, not just work in parallel. A lead agent weighs feedback and records risk choices, while one writer edits shared files. Once humans set boundaries and approve initial check rules, testable runs can go automatically, while humans judge rule relaxations, user experience, and values.

First, we must set clear check rules before work starts. Without a clear end goal, an agent may keep making code, commits, or reports without solving the real problem. Commit counts alone do not prove success, so tests must check actual results [Anthropic evals]. Humans approve the first rules and save that version. Agents can propose rule edits with reasons, but edits that relax pass conditions or change goals need new human approval before replacing the old version. Next, each agent reads the same task and human boundaries, then drafts rules alone. In my design, working alone aims to reduce early anchoring from the first answer, even if shared blind spots remain. Agents then compare drafts to expose missed failure cases, conflicts, and hidden guesses. This talk should produce clear check rules, turning testable parts into program tests. Prior work studies independent review and cross-checking [Cognition 2026; Kim v3]; applying them to rule-making is my inference. After that, a lead agent ends the talk to avoid endless debate for full agreement. It can accept leftover risks within approved limits and record the reasons. Still, completion must rely on test results and open issues, not completion claims from agents [Claude Code task status]. While many agents can test or review at once, only one writer edits shared files to avoid overlapping changes and mixed designs [CooperBench / Claude Code docs]. Finally, humans join at key points, not just press enter. After approving initial plans [Klaassen] and setting boundaries for safety, permissions, and values, humans let agents run alone while rules hold. Humans step in again if agents hit boundary limits, need new permissions, propose weaker rules, or need final judgment on user experience and values.

Critics may argue that human review speeds are limited, so frequent approvals become a bottleneck; instead of manual review steps, teams should build safety nets like automated tests and monitoring [Klaassen]. I agree for stable, checkable runs: once rules and boundaries are approved, my workflow skips per-tool confirmations and routine line-by-line code checks. However, passing automated checks only shows work matches given rules; it does not prove those rules fully capture human goals [Böckeler]. Because software serves human needs, I argue that humans—not the building system—should decide initial goals, value trade-offs, and rule relaxations. These checkpoints cost human attention, so I would cut approvals for non-safety rule relaxations if autonomous edits proved faster without failing human outcome checks.

My proposal still has clear gaps and limits. First, my checkpoints cannot stop agents from burning tokens inside approved boundaries, so the design still needs stopping conditions like max step limits [Anthropic effective agents]. Second, cited benchmarks do not test external program checkers or wall-clock time [Kim v3]. Finally, my single-writer rule targets shared code, not splittable tasks where parallel work helps [Kim v3].
